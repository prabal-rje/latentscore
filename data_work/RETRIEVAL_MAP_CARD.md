that powers the default `fast` model. A dataset-card-style index of
what's in the map, how it was built, how to load it, and what it
isn't.

A second related artifact ships alongside:
`2026-01-26_scored/vibe_and_clap_audio_embeddings_to_config_map.jsonl`
- same rows, but with LAION-CLAP audio-embedding vectors (512-dim)
instead of MiniLM text embeddings. Powers the optional `fast_heavy`
model via `pip install latentscore[heavy]`.

## What this is

The retrieval map is a curated index over schema-valid procedural-audio
states. Each row is (text description, embedding, music configuration,
title, color palettes). At query time, latentscore embeds the user's
vibe string via MiniLM, runs a single cosine-similarity scan against
the row matrix, and returns the nearest neighbor's `MusicConfig` (plus
the row's title and palettes as metadata).

The map is **documented infrastructure, not a hidden cache**. The
construction pipeline, the source texts, the scoring methodology, and
the rebuild instructions are all here.

## Row schema

Each line is one JSON object:

| Field | Type | Notes |
|---|---|---|
| `dataset` | string | Source corpus identifier in [Common Pile](https://huggingface.co/datasets/common-pile) (e.g. `common-pile/pressbooks_filtered`). |
| `id_in_dataset` | string | URL or identifier of the source text the vibe was extracted from. |
| `split` | enum | One of `SFT-Train`, `SFT-Val`, `GRPO`, `TEST`. |
| `vibe_original` | string | The natural-language description (variable length, typically 50-300 chars). |
| `embedding` | list[float] (len 384) | MiniLM-L6-v2 unit-normalised text embedding. |
| `title` | string | Title generated by the config-generation LLM for the music piece this row represents. |
| `config` | object | A schema-valid `MusicConfigPrompt` payload - the actual control surface (tempo, mode, root, brightness, instrument styles, etc.). See `latentscore/config.py`. |
| `palettes` | list[Palette] | Three color palettes (each with 5 weighted hex colors) derived from the config + vibe semantics. |

The CLAP variant adds one field:

| Field | Type | Notes |
|---|---|---|
| `clap_audio_embedding` | list[float] (len 512) | LAION-CLAP audio embedding of the audio rendered from this row's `config`. |

## Construction pipeline

Lives entirely in `data_work/`. To rebuild from scratch:

```text
01_download_base_data.py    Sample ~tens of thousands of natural-language
                            texts from Common Pile (pressbooks, government
                            documents, public-domain books, etc.).
       │
       ▼
02a_extract_vibes.py        Use a cheap LLM (gpt-oss-20b or similar) to
                            extract short, evocative "vibe" descriptions
                            from each source text. Multi-level extraction
                            (scope/character). Dedupes on vibe_original.
                            Writes the SFT/GRPO/TEST splits.
       │
       ▼
02b_generate_configs.py     For each vibe, use a SOTA hosted LLM (Claude
                            Opus by default) to generate N=5 candidate
                            MusicConfigPrompt payloads via Best-of-N
                            sampling. Validates format + schema + palette
                            per candidate. Stores all N + scores.
       │
       ▼
02c_score_configs.py        Render audio for each of the N valid candidates,
                            score with LAION-CLAP against the vibe text,
                            re-select best_index based on highest CLAP
                            score. Quality-based Best-of-N.
       │
       ▼
(after splits + dedupe + embedding via MiniLM)
                            Final per-row embedding via
                            sentence-transformers/all-MiniLM-L6-v2,
                            normalized to unit length.
       │
       ▼
HF Hub upload               Push to guprab/latentscore-data at the dated
                            version directory (e.g. 2026-01-26_scored/).
```

`04_clap_benchmark.py` and `06_eval_suite.py` evaluate the resulting
map; they don't write to it.

Approximate cost: a few CPU-hours of pipeline work, plus the hosted
LLM API calls for vibe extraction (cheap) and config generation
(Claude Opus is the expensive step, ~$50-100 for the full 10k-row
pass). Re-running just `02c_score_configs.py` to rescore an existing
map with a different scorer is cheaper (CPU-only).

## Models used in construction

| Stage | Model | Purpose |
|---|---|---|
| Vibe extraction | `gpt-oss-20b` (configurable) | Extract short vibe descriptions from long source texts. |
| Config generation | `claude-opus-4-1` (configurable) | Best-of-N sampling of `MusicConfigPrompt` payloads. |
| Audio scoring | LAION-CLAP (no fusion) | Score rendered audio against vibe text. Best-of-N selection. |
| Text embedding (runtime) | `sentence-transformers/all-MiniLM-L6-v2` | 384-dim unit-normalised embedding used for nearest-neighbour lookup. |
| Audio embedding (heavy variant) | LAION-CLAP | 512-dim audio embedding used by the `fast_heavy` model. |

## How latentscore loads it

`latentscore/models.py` resolves the map via four env vars (defaults
shown):

```python
LATENTSCORE_EMBED_MAP_REPO       = "guprab/latentscore-data"
LATENTSCORE_EMBED_MAP_FILE       = "2026-01-26_scored/vibe_and_embeddings_to_config_map.jsonl"
LATENTSCORE_CLAP_EMBED_MAP_REPO  = "guprab/latentscore-data"
LATENTSCORE_CLAP_EMBED_MAP_FILE  = "2026-01-26_scored/vibe_and_clap_audio_embeddings_to_config_map.jsonl"
```

First call lazily downloads via `huggingface_hub.snapshot_download`,
caches under `~/.cache/huggingface/hub/`. Subsequent calls hit the
cache.

To pin a specific version or point at a fork, set
`LATENTSCORE_EMBED_MAP_REPO=<your-repo>` and
`LATENTSCORE_EMBED_MAP_FILE=<path/to/file>.jsonl`.

To skip the HF download entirely and use a local checkout, drop the
JSONL at `models/all-MiniLM-L6-v2/embed_map.jsonl` (or wherever the
loader's local-first check looks - see `_resolve_embed_map_path()` in
`latentscore/models.py`).

## Known biases and limitations

- **Western / English skew.** Source texts are sampled from Common
  Pile collections that lean English-language and Western-cultural.
  The resulting vibe descriptions inherit that distribution; vibe
  prompts in other languages or referencing other musical traditions
  retrieve less reliably.
- **Procedural-audio bound.** Configurations are constrained to
  what the LatentScore synthesizer can render - layered procedural
  audio with a fixed set of instrument styles. The map cannot express
  arbitrary acoustic outcomes (no realistic piano, no human voice).
- **CLAP-in-the-loop.** LAION-CLAP is used both during construction
  (Best-of-N selection in `02c`) and during evaluation
  (`04_clap_benchmark.py`). Map quality and CLAP-benchmark scores are
  not independent - treat any CLAP-based number as an engineering
  signal, not a perceptual claim. The bulleted ACM MM OSS draft is
  explicit about this; see `submissions/ACM_MM_OSS_paper/bulleted_draft.md` §5.1.
- **LLM hallucination bound.** The config-generation step uses
  Claude Opus. The validity rate before Best-of-N selection is ~70-80%
  (format + schema validation rejects malformed outputs); the final
  map is 100% schema-valid because invalid candidates are filtered.
- **Static.** Versioned by date directory; not continuously updated.

## Distribution and licensing

- Map contents: **Apache 2.0**, matching the `latentscore` source repo.
- Source-text attributions: the `dataset` and `id_in_dataset` fields
  let downstream users trace each row back to its Common Pile source
  for attribution. Common Pile sources carry their own licenses (most
  are CC-BY / public-domain / similar).
- LLM-generated content: outputs from Claude Opus / gpt-oss-20b /
  CLAP. Outputs of those models are released under Apache 2.0 here
  per LatentScore's combined license; users should still respect
  each underlying model's terms when reusing the *training data* (the
  raw N candidates per vibe, not just the selected one - those are
  in `data_work/.experiments/` and aren't published).

## Versioning policy

A new dated version directory (e.g. `2026-03-15_scored/`) is created
when:

- The schema (`MusicConfigPrompt` field set) changes,
- A different scorer / Best-of-N policy is used,
- A different embedding model is used,
- The source-text corpus mix changes substantially.

Minor reruns (same pipeline, more rows) overwrite the existing
version directory.
